# nonation — правила параллельной разработки

Дата старта процесса: **23.10.26**. Репозиторий: https://github.com/alexvelikiy88-sketch/nonation, основная ветка `main`.

Этот файл обязателен для каждого чата/агента. Выполненные действия должны подтверждаться исходниками GitHub, коммитами, CI и PR. Чат сам по себе не является источником истины.

## Единая система координации

- **`TASKS.md` в корне** — сводка проекта. Обновляет **только руководитель (MANAGER)** после проверки PR и фактов.
- **`NONATION_MANAGER.md`** — полномочия руководителя, порядок аудита, утверждения и объединения.
- **`docs/agents/CHAT_01_UNITY_WEBGL.md`**, **`CHAT_02_BACKEND_SIMULATION.md`**, **`CHAT_03_GRAPHICS_UI.md`** — задания трёх исполнительных чатов.
- **`docs/agents/reports/01_UNITY_WEBGL.md`**, **`02_BACKEND_SIMULATION.md`**, **`03_GRAPHICS_UI.md`** — личные журналы исполнителей. Каждый исполнитель изменяет **только свой отчёт** в своей ветке.
- Новая работа: отдельная ветка, коммиты, PR к `main`. Руководитель принимает PR после проверки. **Никто из исполнителей не пушит напрямую в `main` и не изменяет `TASKS.md`.**
- Отчёты в ветках доступны руководителю и до merge. После merge отчёт сохраняется в `main`, и руководитель обновляет сводку.
- В каждом ответе по работе указывать: изменённые файлы, SHA коммита, ссылки на PR/CI, подтверждённые проверки, непроверенное и конкретные блокеры.

## Автоматическая проверка PR — Integration Guard (CHAT 04)

- Каждый PR в `main`, включая изменения только документации, проверяется workflow `.github/workflows/integration-guard.yml` (`Ownership and change integrity`). Он запускает `Tools/pr_integration_guard.py` **из актуального доверенного `main`**, а не из PR. Diff вычисляется от общего предка (`git merge-base`) текущего `main` и PR head: старый `pull_request.base.sha` может быть устаревшим после синхронизации ветки и ошибочно приписывать менеджерские изменения агенту.
- Правила владения читаются из текущего `AGENTS.md` в base-коммите. Новые нераспределённые исходники вне явно разрешённых путей агент вносит после `CROSS-OWNER REQUEST` и назначения владельца руководителем.
- Если менеджеру необходимо изменить закреплённый за агентом файл в отдельном интеграционном PR, описание PR должно содержать `INTEGRATION-EXCEPTION: точный/путь/к/файлу` для каждого такого пути. Менеджер **не меняет** личные отчёты исполнителей.
- **Единоразовый перевод работ в `main` по решению владельца от 24.10.26:** управляющий PR из `manager/full-integration-*` вправе импортировать личные отчёты из точных SHA завершённых веток. На каждый отчёт требуется `AGENT-REPORT-IMPORT: <path> FROM <agent/branch>@<40-character SHA>`; `Integration Guard` проверяет ancestry и точный исходный blob. Допускается только дополнительный раздел `INTEGRATION HANDOFF - CHAT 04 / Manager` с подписью `Author: CHAT 04 / Manager`, без изменения текста агента. Это не право приписывать менеджеру авторство чужой работы и не распространяется на обычные PR.
- Удалять критические C#/scene/config файлы из PR агента запрещено. Менеджер указывает `DELETION-REVIEWED: точный/путь/к/файлу` и обоснование в описании своего PR; это не заменяет ревью.
- При добавлении или замене графического ассета приложить в описание PR `ASSET-LICENSE-EVIDENCE: источник, версия, лицензия, права на распространение`. Наличие записи **не равно** автоматической проверке прав.
- Статический Guard помечает подозрительное исчезновение публичных C# символов предупреждением; это не компиляция Unity или проверка WebGL. Ошибки Guard должны блокировать приёмку PR.
- **GitHub branch protection (проверено 24.10.26):** Ruleset `NONATION — Main Protection` (ID `25749583`) **Active** на ветке `main`; обязательны Pull Request, `Ownership and change integrity`, разрешение review threads. Запрещены удаления ветки и force-push, Required approvals = 0. `Source preflight and .NET 8` пока не required: из-за `paths`-фильтра он не запускается на документационных PR. Не объединять изменения без соответствующих реальных проверок; правила GitHub не заменяют ревью менеджера.
## Рабочий цикл каждого чата

1. В начале **каждого нового сеанса** открыть `AGENTS.md`, `TASKS.md`, свою инструкцию, свой отчёт **из текущей ветки**, свежий `main`, открытые PR и последнее GitHub Actions. Не полагаться на текст в старом чате как на свежую версию.
2. Проверить, что работа идёт строго в закреплённой ветке; если ветка уже отличается от `main`, не сбрасывать свои коммиты.
3. Решать задачи своего направления небольшими осмысленными коммитами; не удалять существующие игровые системы, данные или лицензии без обоснования.
4. Запустить доступные тесты. Если нет Unity Editor, написать **«проверено статически / .NET CI»**, а не **«Unity WebGL работает»**.
5. После каждого логического этапа обновить свой отчёт: статус, файлы, SHA, тесты, blockers, последующие шаги. Коммитить отчёт **вместе** с изменениями.
6. Создать или обновить PR `agent/... → main`; не делать merge самому. В описании PR указать риски, совместимость, факты из CI и связанный отчёт.
7. Если инструмента/доступа не хватает, обозначить блокер и безопасный следующий шаг; не выдумывать результаты и не требовать вручную редактировать C#.

## Технические запреты

- Без взлома лицензирования Unity; не публиковать секреты, токены, приватные архивы.
- Не переносить Honda CC BY-NC-SA, Maid/GIGN/Pinkdress и другие ассеты с невыясненными правами в публичную игру.
- Не называть `GitHub Actions source-validation: success` доказательством компиляции Unity: в последних запусках WebGL-работы были `skipped`.
- Не менять одновременно несколько высокорисковых слоёв ради косметических улучшений.
- Не использовать `tasks.html`: центральный файл — **`TASKS.md`**.
- Дата в статусах: **дд.мм.гг**, без времени.
- Реалистичные персонажи важны, но нельзя подменять их процедурными капсулами и выдавать за готовую графику.
